# Small-Data Time-Series Forecasting on Snowflake

> **All data in this repository is 100% synthetic.** Every row is generated by
> `01_generate_synthetic.py` from a documented statistical process (multiplicative
> seasonality, Negative Binomial noise). There is **no real patient data, no PHI,
> and no PII** anywhere in this repo — the healthcare setting is a realistic
> stand-in, nothing more. No credentials are stored here either:
> `snowpark_session.py` reads your local `~/.snowflake/connections.toml` at
> runtime; nothing sensitive is committed.

A working reference for time-series forecasting in the **small-data regime**
(<10,000 records), where variance — not bias — is the dominant error term and
most standard forecasting guidance actively hurts. It benchmarks two complete
forecast stacks on identical rolling-origin windows, runs a walk-forward
learning loop with drift detection, and registers the champion to the Snowflake
Model Registry.

**Who this is for:** ML engineers who know what a MASE is and why a random
train/test split on time series is malpractice.

## Results at a glance

6,576-row synthetic panel: 6 hospital departments × 1,096 daily observations.

| | MASE | note |
|---|---|---|
| Irreducible floor (perfect model) | 0.6648 | computable only because data is synthetic |
| **AutoGluon champion** (`high_quality`) | **0.7448** | captured 60.4% of achievable gain |
| **`SNOWFLAKE.ML.FORECAST` + covariates** | **0.7694** | statistically tied (p=0.085) — and it's pure SQL |
| Zero-shot Chronos | 0.7825 | 8 seconds of "training" |
| Chronos fine-tuned | 0.8469 | ✗ fine-tuning made it *worse* |
| Best baseline (`seasonal_mean_4w`) | 0.8667 | a strong bar, not a straw man |

Plus two measured negative results that matter more than the ranking:
**fine-tuning the foundation model hurt (+8.2%)** and **retraining on a schedule
hurt (+1.5%)** — the two things a team in this regime is most likely to do by
default. Details in §4.

## 1. Deploy & run

### Prerequisites

- Python 3.11+ and a Snowflake account with a warehouse and `CREATE SCHEMA` on
  one database.
- A connection defined in `~/.snowflake/connections.toml` (any auth method —
  password, key pair, or `externalbrowser`; `snowpark_session.py` handles all of
  them).

### Setup

```bash
git clone git@github.com:sarathi-aiml/ML-Forcasting-small-dataset.git
cd ML-Forcasting-small-dataset
./setup_env.sh          # creates .venv with pinned deps
./install_ag.sh         # AutoGluon-timeseries (handles the macOS arm64 xgboost gap)
```

### Run the pipeline

Point at your own database/schema first — edit `DATABASE` / `SCHEMA` at the top
of each `0*.py` (defaults: `HEALTHCARE.ML_FORECAST`). Then, in order:

```bash
.venv/bin/python 01_generate_synthetic.py   # 6,576-row synthetic panel -> Snowflake
.venv/bin/python 02_eda_quality_gates.py    # EDA + automated data-quality gates
.venv/bin/python 03_features.py             # calendar/Fourier features (384 -> 17)
.venv/bin/python 05_trial_automl.py         # 6-trial AutoML ladder (~43 min)
.venv/bin/python 06_snowflake_forecast.py   # SNOWFLAKE.ML.FORECAST track (SQL-native)
.venv/bin/python 07_compare_report.py       # significance-tested comparison + plots
.venv/bin/python 08_learning_loop.py        # walk-forward loop: drift detect + gated retrain
.venv/bin/python 09_log_experiments.py      # all runs -> Snowflake experiment tables
.venv/bin/python 10_register_model.py       # champion -> Snowflake Model Registry
```

Every stage writes its outputs to `artifacts/` (metrics, leaderboards,
predictions) and `plots/` (12 diagnostic figures), so you can inspect results
without rerunning anything.

## 3. Why this is useful

Small datasets flip the usual playbook. This repo demonstrates — with measured
numbers, not assertions — which techniques pay off below ~10K records:

| Technique | Mechanism | Measured effect |
|---|---|---|
| **Cross-series pooling** | 6,576 training points instead of 1,096 | 0.8345 → 0.7576 (**−9.2%**) |
| **Zero-shot foundation model** | Pretraining substitutes for data you don't have | 0.8345 → 0.7825 (**−6.2%**), in 8s |
| **Ensembling** | Averages away estimation variance | 0.7576 → 0.7454 (−1.6%) |
| **Cyclical/Fourier encoding** | 384 → 17 features; 29.6:1 obs-per-feature | enabler for the above |
| **Rolling-origin eval** | 36 test cells instead of 6 | no accuracy gain — buys *trustworthy ranking* |
| **Fine-tuning Chronos** | — | **+8.2% worse** — negative result |
| **Retraining on schedule** | — | **+1.5% worse** — negative result |

### The recommendation table

| Situation | Pick | Why |
|---|---|---|
| Default / production | **`SNOWFLAKE.ML.FORECAST` + engineered covariates** | statistically tied with the AutoML champion; pure SQL; nothing to deploy |
| Need full quantiles | `high_quality` AutoGluon | FORECAST returns a single interval; WQL/CRPS need quantiles |
| Cold start, no history | Zero-shot Chronos | 0.7825 MASE with 8s of "training" |
| Explainability required | Classical (AutoETS) | decomposable trend/seasonality |
| — | ~~fine-tuned Chronos~~ | worse *and* biased. Don't. |

The headline finding for Snowflake shops: **the pure-SQL
`SNOWFLAKE.ML.FORECAST` path with good covariate engineering is statistically
indistinguishable from a 43-minute AutoML search** (Wilcoxon p=0.085 across 36
paired window×department cells) — with no Python runtime, no dependency
management, and nothing to containerize. Covariates are where the effort should
go, not model search.

## 4. The two negative results, in detail

### Retraining on a schedule made it worse

13 walk-forward steps × 28 days, traversing a simulated flu surge:

| Strategy | mean MASE | vs never retraining | refits |
|---|---|---|---|
| **Never retrain** | **0.9076** | — | 0 |
| Drift-triggered | 0.9165 | −0.98% | 2 |
| Retrain every step | 0.9216 | −1.54% | 13 |

Refitting on ~1,100 observations resamples estimation noise without adding
signal. The champion/challenger gate did the real work: of 10 fired triggers only
2 promoted — **the gate blocked 8 harmful refits**. If you take one piece of the
retraining machinery from this repo, take the gate (`08_learning_loop.py`).

### Drift detection: KS two-sample beat Page-Hinkley

The KS detector alarmed exactly during the surge and stayed quiet otherwise.
Page-Hinkley required per-deployment calibration to be usable at all — its
textbook threshold sits *below the noise band* when each step contributes many
observations. Rule of thumb if you use PH: `λ > 3·√(observations per step)`.

## 5. Metrics reference (what's in `forecast_metrics.py`)

- **MASE** — ranking metric. Scale-free, baseline-anchored; safe to average
  across series of different scales.
- **RMSSE, sMAPE, MAE, RMSE** — reported for completeness; MAPE is reported but
  never used for selection (it rewards under-forecasting).
- **ME / MPE** — signed bias, catches models that are accurate but consistently
  high or low.
- **WQL, CRPS** — probabilistic quality across quantiles.
- **PICP / MIS** — do the prediction intervals actually cover at the stated rate,
  and how wide are they when they miss.
- **Conformal intervals** — distribution-free coverage wrapper; measured effect
  here was mixed (better in aggregate, worse per-series).
- **Irreducible floor** — the oracle MASE (0.6648) computed against the true
  generating process, which is only possible on synthetic data. It turns "MASE
  0.74" into "we captured 60% of what is achievable" — a far more honest way to
  report model quality.

## 6. Running this on your own real data

1. Replace `01_generate_synthetic.py` with a loader for your table — the
   contract downstream is simply `(series_id, date, target)` plus optional
   known-future covariates.
2. Re-run `02` (the quality gates will tell you if your data breaks the
   assumptions — gaps, negatives, insufficient history).
3. Keep the rolling-origin evaluation exactly as is. It is the part most worth
   porting.
4. Expect the *relative* technique ranking (pooling > zero-shot > ensembling;
   don't fine-tune; don't retrain blindly) to transfer; the absolute numbers will
   not. You cannot compute the irreducible floor on real data — use the best
   baseline as your reference bar instead.
5. Holiday/event calendars are pluggable (`holidays` package) — swap in your
   region and domain events in `03_features.py`.

## 7. Limitations, stated plainly

- Results are measured on one synthetic process; treat them as a **methodology
  reference**, not universal constants.
- The synthetic process is stationary apart from the seasonal surge — real data
  with genuine regime changes will reward retraining more than §4 suggests.
- `SNOWFLAKE.ML.FORECAST` exposes a single prediction interval; if your consumers
  need calibrated quantiles, that constraint decides the stack before accuracy
  does.
